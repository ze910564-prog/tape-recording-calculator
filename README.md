# 磁带录制计算器

手边一堆无损曲库，想挑一批歌录满一盘磁带（或者只是想确认"这些歌塞得下吗"）。
这个工具干的就是这件事：**从你的库里选歌 → 实时告诉你能不能录下 → 装不下的地方差多少秒**。

按需求约定，它**只做判定、分配、诊断，绝不自动改你的选择**。

---

## 改完代码要重启服务

**前端每次刷新都会重新下载 `app.js`，但服务是个常驻进程。** 改了 `server.mjs` 或 `lib/` 之后
不重启服务，它会一直跑旧逻辑 —— 界面是新的、算出来的是旧的，
各种「明明该 X 却显示 Y」都从这来。

两道保险：

1. 服务把自己的启动时间戳交给前端比对，**发现你重启过服务，界面会自己刷新一次**
2. `index.html` 里的 `/app.js`、`/style.css` 引用带 `?v=<启动时间>`，**重启后浏览器必定重新下载**，
   不会拿缓存里的旧脚本。静态资源一律 `no-store`

如果界面出现莫名其妙的矛盾，先看一眼那个服务窗口是不是好久没关过了。

## 环境要求

- **Node.js 18 或更新**（用到 `structuredClone`）
- **零依赖**：不需要 `npm install`，也不需要 ffmpeg / ffprobe
- 启动脚本是 Windows 的 `.cmd` / `.ps1`；服务本体只用 Node 标准库，换平台手敲 `node server.mjs` 即可

## 快速开始

**双击 `启动.cmd`** 就行。

它会检查 Node 环境、在端口被占用时自动换端口、等服务真的能访问了再打开浏览器。
服务跑在一个独立的窗口里（能看到它的输出），**关掉那个窗口就等于停止服务**。

手动启动也可以：

```powershell
cd tape-recording-calculator
node server.mjs              # 默认 7788
node server.mjs --port 8080  # 指定端口
```

停止：

```powershell
node tools/stop.mjs
```

它通过 HTTP 口令请求服务退出，不依赖 netstat / taskkill，
所以服务记在哪个端口都能找到（端口和口令写在 `.cache/config.json` 里，每次启动换一次）。

启动脚本的参数：`-Port 8080` 指定端口、`-Foreground` 在当前窗口前台运行、`-NoBrowser` 不自动开浏览器。

> 为什么启动脚本是纯英文的：Windows PowerShell 5.1 在没有 BOM 时按 ANSI 读 `.ps1`，
> 中文字符串会被读成乱码并破坏引号配对，而编辑器和补丁工具会悄悄丢掉 BOM。
> 干脆让 `启动.cmd` 和 `start.ps1` 保持纯 ASCII，中文只出现在文档和界面里。

首次启动会自动扫描曲库（几百首约 20 秒，有缓存后是秒开）。曲库路径在 `.cache/config.json` 里，
也可以在界面左上角用 `＋` 添加、用下拉框切换。

## 时间模型（这块是整个工具的核心，值得先读）

磁带上"一首歌占多长"不是它自己的时长，而是它加上前后的间隔：

```
第 i 首的起点 = 起始引导 + i × 歌间留白
```

- **起始引导**只在 A 面开头算一次（有些机器按下录音后要走带一小段才稳定）
- **歌间留白**是歌与歌之间的间隔，**最后一首之后不再追加**
  —— 否则末尾那点空白会被当成必须留出的空洞，白白挤掉一首歌

### 容量怎么算

两面等长，所以单面容量 = 总容量 ÷ 2。总容量由「标称 + 档位」决定，两种模式：

| 模式 | 算法 | 例子 |
|---|---|---|
| 准确数值 | 标称 + 档位秒数 | 120 分 `-1m` → 119 分 |
| 百分比 | 标称 × (1 + 档位百分比) | 90 分 `-1m` → 88.2 分 |

档位是 `+1m / +30s / 标称 / -30s / -1m`。准确数值模式是给"我就按 119 分算"这种直觉用的；
百分比模式适合"带子大概比标称短 2%"这种相对判断。两种随时切，切模式不改你的操作习惯。

**为什么要留档位**：磁带实际长度受带厚和走带速度影响，标称 120 分的带子实际可能是 118～122 分。
保守一点不会在最后一首上翻车——录到带尾是直接截断，不是自动跳过。

### 装带怎么分两面

磁带是两面独立录的，所以"总量够"不等于"装得下"——还要能切成一前一后两段。

**手动顺序（默认）**：保持你排的顺序，搜索一个最佳折点，让 A 面尽量满、剩下的 B 面也装得下。
取"最大可行 k"意味着浪费最少。这比"顺序填满 A 面"更合理：后者常见的结果是 A 面 59.95 分、
B 面 48 分，白白浪费十分钟带长。

**自动排布（按钮）**：实在分不下时，允许软件重新划分两面（选歌一首不删，只是换个装法）。
用到它时判定面板会明确标注"这份装法由自动排布给出，顺序与你的手动排列不同"。

### 两面分配：塞满 vs 均衡

顶栏的「两面分配」只有两档，**机器差异写在选项文案里**（哪档适合哪种机型）：

| 分配方式 | 效果（20 首共 87 分、120 分带子） |
|---|---|
| **塞满 A 面**（自动/手动反面机） | A 面 53.99 分 / B 面 33.05 分，两面差 20.94 分 |
| **两面均衡**（仅手动反面机） | A 面 43.50 分 / B 面 43.55 分，两面差 **2.4 秒** |

> **为什么没有"录音机类型"开关**：它曾经存在过，但从未参与任何计算 —— 只影响
> "要不要用均衡"和"按钮灰不灰"。那是个纯 UI 状态，却把状态空间从 2 种撑成 6 种，
> 状态互相打架的 bug 全出在那多出来的一维上。删掉它，改用文案标注，更直接也更难出错。

**均衡的真正用处**：A 面正向走到带尾，翻过来 B 面从带尾往回走，B 面放完磁头正好回到带头
—— 也就是 A 面的开头。所以只要两面音乐时长相等，翻面之后紧接着就是 A 面第一首，
完全不用倒带。塞满模式下两面差二十多分钟，翻面后就得倒回去一大段。

**均衡不缩减可录总量**：两面是两条独立音轨，各自都有一面容量，总共两面容量都能用。
「均衡」只是把选好的歌**分摊**到两面，一首都不会因为选了均衡而丢掉。
（这点和直觉相反：两面各占一半指的是"时长相等"，不是"每面只准用半盘"。）

**均衡的分配是搜出来的，不是对半分**：理想目标是「选歌总量的一半」（上限才是单面容量），
然后二分 A 面预算直到 B 面刚好装得下，取那个最接近的划分。所以：

- 7 首共 5 分钟的歌 → 各 2.5 分钟左右（而不是全塞进 A 面、B 面空着）
- 16 首共 87 分钟 → 各 43.5 分钟左右

**总量确实装不下整盘时**，均衡让位给装载量：两面各自按单面容量取最大子集，
先尽可能多录（实测均衡与塞满的装入总量一致），再在这个前提下尽量让两面接近。

**一个副作用**：内容刚好卡满整盘时，均衡反而比塞满更容易成功。实测 34 首（119.7 分 /
120 分）—— 塞满模式判定"需要重排"（A 面装到 59.94 分后剩 2 秒放不下任何歌），
而均衡一次就装下了（A 59.83 / B 59.85）。因为均衡天然把内容摊开，避开了那种边界。

## 判定结果怎么看

三档结论：

| 结论 | 含义 |
|---|---|
| **录得下** | 按你排的顺序就能装进两面，绿了 |
| **需要重排** | 总时长够，但当前这个排法分不进两面。按「自动排布」即可，一首都不用删 |
| **录不下** | 容量真的不够。会告诉你超了多少秒、最少要少录几首、以及删哪几首代价最小 |

右侧的**剩余**是实时值，按「实际装进两面的时长」算，不是拿总容量减去总需求——
后者在装不下的情况下会给出负数，没有意义。进度条快满时会变色提醒。

诊断给的是**数字和建议，不会替你改清单**：

- 超出多少秒
- 最少要少录几首
- "删掉某一首刚好够"的候选（按删后余量从小到大排，余量越小越划算）
- 有哪些歌因为**单曲超过单面容量**而无论怎么排都放不进去

### 两个控件是一件事

「两面分配」和「自动排布」描述的都是**同一件事：这盘带按什么规则装**。
它们之间有约束关系，界面会自动维持一致：

| 两面分配 | 自动排布按钮 |
|---|---|
| 塞满 A 面 | **可点** —— 在"按你排的顺序"和"软件重新划分"之间切换 |
| 两面均衡 | **可点** —— 点它会切到「塞满 + 自动排布」并说明原因 |

均衡和自动排布是**两种互斥的排法**（前者按时长划分、后者按顺序划分）。切换到均衡时，
自动排布会自动关闭并弹提示说明 —— 关键是"说出来"，而不是静默清掉：
悄悄改掉用户刚点的东西，就会出现"点了又弹回来"那种说不清的现象。

### 自动排布做了什么

按下「自动排布」后：

- 中间清单**切换成软件排好的顺序**，不再是你的点选顺序（否则看到的和右侧对不上，等于白排）
- 被挪动过的曲目**序号标黄**，副标题里写出它原来排第几位
- **同一面内仍然可以拖动微调** —— 比如把 A 面里的两首歌互换。跨面搬运会被拒绝：
  那会把刚算好的两面时长差拉开，等于让均衡作废；要改就到顶栏改分配方式或增减选歌
- 再按一次按钮回到手动顺序

> 高亮刻意做得很轻（只有序号变色 + 极淡底色）：均衡模式会重排大部分曲目，
> 用重边框铺满一屏反而看不清重点。
>
> 高亮的判断依据是「自动模式有没有生效」（后端 `autoApplied`），不是「顺序有没有变」
> （`reordered`）。这两个是分开的：你拖动微调之后，服务端算出的顺序可能恰好等于你的顺序，
> `reordered` 会变 false，但自动装带仍然在生效 —— 那时候高亮不该消失。

## 导出清单

写磁带标签（J-card）用。判定面板底部有三个格式：

| 格式 | 内容 | 用途 |
|---|---|---|
| **文本清单** | 面 / 序号 / 标题 — 艺人，带时长和起始时间轴 | 直接照着写标签 |
| **CSV 表格** | 面、序号、标题、艺人、专辑、时长、起始、文件名、完整路径 | 丢 Excel 里自己排版 |
| **M3U 播放列表** | `#EXTINF` + 绝对路径 | 录之前先按顺序听一遍 |

文本和 CSV 带 UTF-8 BOM，Excel 打开不乱码。文件名形如 `磁带清单-120分-2026-09-25.txt`。

导出的内容和界面上看到的**完全一致**：服务端判定和导出共用同一段逻辑，
连"没有标签的曲目退回文件名并剥掉扩展名"这种细节都一致。

## 时长是怎么读出来的

**不依赖 ffmpeg，纯 JS 解析文件头。** 三个理由：几千个文件逐个 spawn 进程慢一个数量级；
机器上不一定有 ffprobe（很多整合包只带 ffmpeg.exe）；无损格式的时长本来就能从头部精确算出来。

支持格式：

| 格式 | 依据 | 精度 |
|---|---|---|
| FLAC | STREAMINFO 的采样率与总采样数 | 精确 |
| DSF | fmt 块的位率与采样数 | 精确 |
| DFF | PROP(SND) 里的 FS/CHNL + DSD 数据块长度 | 精确 |
| WAV | fmt 块的 byteRate 与 data 块长度 | 精确 |
| AIFF | COMM 帧数 ÷ 80 位扩展浮点采样率 | 精确 |
| MP3 | Xing/Info 帧数（VBR）；无 Xing 时按 CBR 估算 | 精确 / 估算 |
| M4A/MP4 | moov.mvhd 的 duration ÷ timescale | 精确 |
| AAC(ADTS) | 累计帧数 × 1024 ÷ 采样率 | 估算（只统计已读窗口） |
| OGG | 尾页 granule position | 精确 |

解析格式时踩过的坑都写在代码注释里了，最典型的三条：

1. **DSF 的 fmt 数据区从偏移 40 开始**（chunk header 12 字节 + version 4 字节），不是 28+12
2. **DFF 每个块头的 size 是 8 字节大端**，不是 4 字节；且 CMPR 块的载荷是文本 `"not compressed"`，
   照文本首字节当位深会算出 110bit 的荒谬结果（DSD raw 恒为 1bit/样本）
3. **MP3 的 ID3v2 可能很大**（本机实测有 130KB 的），头部读取窗口必须够大，
   否则跳完标签已经没数据可搜

### 封面

FLAC 的 PICTURE 块、ID3v2 的 APIC 帧、MP4 的 covr atom 都能读，
**DSF/DFF 的 ID3 常挂在文件尾部**，所以尾部也要找。

提取是**懒加载**的：扫描时只记录封面在文件里的位置和大小（便宜），界面请求哪首才提取哪首，
结果落盘缓存。这样缓存 JSON 不会因为 500 多张封面膨胀到几十 MB。

`dataOffset` 的语义是**相对于传入 buffer 起点的偏移**——头部窗口基址为 0 时等于绝对偏移，
尾部窗口必须换算。这里踩过坑：尾部 ID3 的封面曾被当成绝对偏移去读，取回一堆垃圾字节，
所以现在加了一道图片签名校验，缓存文件名带版本号。

## 缓存

- `.cache/library.json`：曲库缓存。失效判据是 `相对路径 + mtime + size`，
  只有新增或改动过的文件才重新解析。切磁带参数时**零重扫**。
- `.cache/covers/`：封面图片缓存，文件名带版本前缀。
- `.cache/config.json`：曲库路径、磁带参数。

想强制重建：界面上点 `↻` 选"确定"，或

```powershell
node tools/test-scan.mjs --force "<你的曲库目录>"
```

缓存里删掉的文件记录会在下次扫描时自动清理，不需要手动维护。

## 自检脚本

脚本的目录参数可以省略：省略时读环境变量 `MUSIC_DIR`，都没设就用当前目录下的 `music`。

```powershell
node tools/test-duration.mjs "<你的曲库目录>" 3   # 时长解析抽查
node tools/test-tags.mjs "<你的曲库目录>" 2       # 标签与封面读取抽查
node tools/test-scan.mjs --force            # 全量重扫并统计
node tools/test-cover.mjs                   # 封面提取字节校验
node tools/test-plan.mjs                    # 判定逻辑的 7 个场景
node tools/test-consistency.mjs             # 判定/顺序/高亮三者与实际装法是否一致（需服务在运行）
node tools/test-fill-mode.mjs               # 两面分配：塞满 vs 均衡的端到端对照（需服务在运行）
node tools/test-verdict-sweep.mjs 3000      # 随机采样 3000 组，撞判定误报
node tools/test-export.mjs                  # 三种导出格式（需服务在运行）
node tools/test-api.mjs                     # 端到端 API（需服务在运行）
node tools/test-render.mjs                  # 无头渲染 + 界面联动 + 服务重启检测
node tools/verify-start.mjs                 # 启动器文件完整性
node tools/lint.mjs                         # 静态检查（语法/未用导入/踩坑写法/无限递归）
node tools/lint-ui.mjs                      # 前端元素 id 与资源引用一致性
```

`test-verdict-sweep.mjs` 值得单独说一句：「明明装得下却报需要重排」这类误判，
手点几个案例是发现不了的，它只在特定时长组合下出现。这个脚本用固定种子随机采样几千组去撞，
判据包括四种：总量够却判录不下、重排能装下却判没装下、判录得下却有歌没排入、
以及诊断说"救不了"但重排其实装得下。

`test-export.mjs` / `test-api.mjs` 可以用 `BASE` 指定别的端口：

```powershell
$env:BASE='http://127.0.0.1:7793'; node tools/test-export.mjs
```

诊断格式时用得上：

```powershell
node tools/dump-head.mjs <文件> 256   # 十六进制 dump 文件头
node tools/dump-dff.mjs <文件>        # 遍历 DFF 块结构
node tools/probe-dff.mjs <文件>       # 探查 DFF 关键偏移
node tools/probe-mp3.mjs <文件>       # 定位 ID3 结束位置并扫同步字
node tools/probe-cover.mjs <文件>     # 拆解 APIC 帧的偏移计算
```

## 已知限制

- **只支持磁带**。MD 的需求中途砍掉了，容量模型里没有 MD 的 SP/LP2/Hi-MD 这些模式。
- **服务只绑定 127.0.0.1**，手机/其他设备访问不了。想远程用得自己处理网络和信任边界。
- **DP 划分是保守的**：子集和模型无法精确表达"只有 k-1 个间隔"，所以按每首选中的曲子都预留 gap 计算。
  结果是宁可少装也不越界 —— 越界在磁带上不可恢复（歌会被截断），这个取舍是有意的。
- **AAC(ADTS) 的时长是估算值**：只统计已读窗口内的帧，长文件会偏短。
- **"最少删几首"是贪心近似**（优先去掉最长的），不是全局最优解。
- 曲库列表没有做虚拟滚动，几千首以上的库会有点卡。

## 与原始需求的对应

| 需求 | 实现 |
|---|---|
